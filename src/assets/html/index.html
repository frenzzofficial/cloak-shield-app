Authentication your backend team can actually own.

cloak-shield is a lightweight, scalable authentication service built on Elysia, Drizzle ORM, PostgreSQL and TypeScript — the login, session and token layer most teams rebuild from scratch, done once, done properly.

// issue a session after credential check
const session = await cloakShield.auth.login({
  identifier: "dev@company.com",
  method: "email",
  password,
});

// cookie-based JWT, rotated on use
res.cookie("cs_session", session.token, {
  httpOnly: true,
  secure: true,
  sameSite: "lax",
  maxAge: 60 * 60 * 24 * 7,
});

// refresh silently, no re-login
await cloakShield.auth.refresh(session.refreshToken);
// why cloak-shield exists

Auth is small enough to seem simple, and dangerous enough to get wrong.

Most teams don't want to build authentication — they want it to already be built. But off-the-shelf identity platforms bring vendor lock-in, opaque pricing and a runtime you don't control, while rolling your own means re-deriving password hashing, token rotation and session invalidation under deadline pressure.

cloak-shield sits in between. It's a service you deploy inside your own infrastructure — Postgres you already run, TypeScript your team already reads — with the hard parts of session and token management handled correctly from the first commit.

// the session lifecycle

What happens on every login, in order

This is the actual sequence a request goes through — nothing hidden, nothing implied.

01

Credential check

Email/phone + password (or code) validated against salted, hashed records — never stored or logged in plain text.

02

Identity verified

A short-lived verification step confirms the account is active and not locked, rate-limited or flagged.

03

Session issued

A signed JWT is set as an httpOnly, secure cookie — never exposed to client-side JavaScript.

04

Token rotated

Each refresh invalidates the previous token, so a leaked token has a short, bounded lifetime.

// how it's built, not just what it does

Production discipline, added one layer at a time

Each piece below was added deliberately, and each one earns its place — here's what it does and why it's there.

01

TypeScript, strict mode strict: true

No implicit any, no silent nulls. Errors surface at compile time instead of in a customer's session.

02

Biome lint + format

One fast tool replaces a separate linter and formatter, so every file in the repo reads the same way regardless of who wrote it.

03

Husky + lint-staged pre-commit

Checks run on the files you're actually committing, before they land — problems get caught locally, not in review.

04

commitlint conventional commits

Enforced commit structure means changelogs and version bumps can be generated from history instead of written by hand.

05

Architecture checks dependency-cruiser

Rules stop a route from reaching into another feature's internals, so the modular structure stays modular as the codebase grows.

06

Tests unit + integration

Auth logic — hashing, token rotation, session expiry — is the last place you want a regression to ship unnoticed.

07

CI on every push

Lint, typecheck and test all run before a branch can merge — the same gate for every contributor, every time.

08

Docker reproducible builds

What runs in CI is what runs in production — no "works on my machine" gap between environments.
